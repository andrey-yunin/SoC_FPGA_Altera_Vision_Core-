# Tcl и описание IP в Platform Designer

Обновлено: 2026-11-06.

Это рабочий учебный материал для embedded/FPGA-разработчика, который пишет на VHDL. Разбираем Tcl по реальному [описанию SDRAM-компонента](fpga/sdram_controller_altera14_hw.tcl), связывая команды с действиями GUI и аппаратной архитектурой.

Задача — понимать каждую настройку и уметь проверить её последствия. Примеры в документе не являются автоматически внесёнными изменениями проекта. Настройки и код пользователь вносит сам, ассистент объясняет и проверяет результат.

## Текущая точка разбора

Схема `memory_subsystem` структурно проверена. Через GUI добавлен `SIM_VERILOG` с исходным Verilog и включён `isMemoryDevice`. Валидация выявила недостающее свойство `TOP_LEVEL` у `SIM_VERILOG`; пользователь добавил его вручную. Повторная проверка завершилась без ошибок и предупреждений. Оба fileset теперь задают `RAMSYS_new_sdram_controller_0`. Копирование списка файлов не задаёт автоматически все свойства набора: результат нужно проверять валидатором. По последнему решению сначала настраиваем компонент через GUI, затем проверяем и подробно разбираем конечный Tcl. Ручное редактирование не является способом по умолчанию.

Перед закрытием Component Editor сохраняем описание компонента через Finish, а перед закрытием Platform Designer сохраняем систему через Ctrl+S. **Generate HDL — отдельная операция; для закрытия окна она не нужна.** Описание IP для синтеза/симуляции подготовлено и проверено. К генерации переходим отдельным следующим практическим блоком после выбора её параметров; повторная генерация синтезной и Verilog-модели уже выполнена пользователем и проверена. Предупреждение старого GUI-каталога устранено после перечитывания IP; компиляция и симуляция модели ещё впереди. Это будет подготовка модели, а не разрешение прошивать плату.

Материал ниже подготовлен к обсуждению. Наличие раздела не означает, что тема уже разобрана с пользователем или настройка проверена экспериментом.

## Где выполняется Tcl и что он описывает

VHDL и Verilog описывают аппаратуру. Tcl в данном файле управляет инструментом разработки: регистрирует IP, перечисляет исходники и объясняет Platform Designer назначение интерфейсов. Команда Tcl сама по себе не превращается в регистр или вентиль FPGA.

Например, строка:

```tcl
set_interface_property reset synchronousEdges DEASSERT
```

задаёт контракт интерфейса сброса. Она не вставляет синхронизатор внутрь нашего исходного Verilog. Platform Designer использует описание при проверке и построении системы; нужную аппаратуру сброса мы отдельно добавили компонентом `reset_controller`.

В проекте есть несколько разных артефактов:

| Файл | Назначение |
| --- | --- |
| `RAMSYS_new_sdram_controller_0.v` | RTL контроллера и его входного FIFO |
| `sdram_controller_altera14_hw.tcl` | Описание одного IP для каталога и генератора |
| `memory_subsystem.qsys` | XML-описание экземпляров и соединений системы |
| `vision_core_top.qsf` | Назначения и настройки ревизии проекта Quartus |
| `vision_core_top.vhd` | Будущий верхний HDL-модуль проекта |
| Будущий `.sdc` | Тактовые и другие временные ограничения для анализа |

Команды API зависят от окружения: обычный `tclsh` не знает `add_interface`, а Tcl Console Quartus не следует считать редактором `_hw.tcl`. Нужные команды предоставляет соответствующий инструмент или пакет.

## Блок 1 Команда и её аргументы

Реальная строка нашего файла:

```tcl
set_module_property NAME sdram_controller_altera14
```

Это команда с двумя аргументами:

| Часть | Значение |
| --- | --- |
| `set_module_property` | Имя команды API Platform Designer |
| `NAME` | Первый аргумент: какое свойство задаём |
| `sdram_controller_altera14` | Второй аргумент: значение свойства |

Пробелы разделяют слова. Первый элемент команды — имя выполняемой команды; остальные передаются ей как аргументы. Количество и смысл аргументов определяет сама команда.

Термин `NAME` здесь не является специальным словом языка Tcl. Это имя свойства, которое понимает API Platform Designer. По той же причине `TOP_LEVEL`, `WORDS` и `DEASSERT` нельзя изучать только по справочнику языка: их смысл задаёт API инструмента.

Обычно одну команду записывают на строку. Несколько команд также можно разделять `;`, но в описании компонента отдельные строки удобнее для чтения, проверки и сравнения изменений.

### Пробелы внутри значения

```tcl
set_module_property DISPLAY_NAME "SDR SDRAM Controller (Altera RTL)"
```

Кавычки объединяют название с пробелами в одно значение. Они не передаются как часть названия. Без группировки слова разбились бы на дополнительные аргументы и команда получила бы неправильный вызов.

Пустые кавычки тоже имеют значение:

```tcl
set_interface_property clock EXPORT_OF ""
```

Здесь передан третий аргумент — пустая строка. Это не то же самое, что пропустить аргумент. Точный смысл пустого значения определяет свойство `EXPORT_OF`; его разберём в блоке интерфейсов.

### Кавычки и фигурные скобки

Tcl поддерживает подстановку переменных и результатов команд:

```tcl
set component_name sdram_controller_altera14
puts $component_name
puts [expr {1280 * 800 * 2}]
```

`set` сохраняет значение переменной, `$component_name` подставляет её значение, а квадратные скобки выполняют вложенную команду и подставляют результат. Последняя строка выводит `2048000` — размер нашего примера кадра в байтах.

Двойные кавычки группируют значение, сохраняя подстановки. Фигурные скобки группируют текст без обычной подстановки `$` и `[]` на этом этапе:

```tcl
puts "$component_name"
puts {$component_name}
```

Первая строка выводит значение переменной, вторая — буквальный текст `$component_name`. Перенос строки с обратной косой чертой имеет отдельные правила; к нему вернёмся при разборе длинных команд.

Эти примеры иллюстрируют синтаксис. Выполнять ими изменение проекта не требуется.

### Комментарии

```tcl
# file sets
```

Такой комментарий поясняет следующий участок файла и не создаёт настройку. `#` распознаётся как начало комментария там, где Tcl ожидает начало команды; не следует считать его универсальным признаком комментария в любом месте строки.

Заголовок `DO NOT MODIFY` добавил Component Editor. Ручная правка технически возможна, но последующее сохранение из GUI может перезаписать её. Перед ручным изменением закрываем Component Editor; затем проверяем реальный сохранённый файл, а не только состояние GUI.

## Загрузка пакета qsys

В нашем описании есть:

```tcl
package require -exact qsys 16.1
```

| Часть | Значение |
| --- | --- |
| `package` | Команда языка Tcl для работы с пакетами |
| `require` | Запросить загрузку нужного пакета |
| `-exact` | Запросить именно указанную версию API |
| `qsys` | Имя пакета, предоставляющего команды описания компонента |
| `16.1` | Версия API пакета в этом файле |

После загрузки пакета становятся доступны команды вроде `set_module_property`, `add_fileset` и `add_interface`.

**`16.1` не означает, что мы устанавливаем или запускаем Quartus 16.1.** Файл создан редактором 25.1, который выбрал поддерживаемую версию API. Это также не версия исходного контроллера: его RTL получен от IP Altera 14.0, а наша упаковка имеет версию `0.1`.

Менять число API только для совпадения с номером установленного Quartus не нужно. Изменение версии API требует проверки совместимости используемых команд и свойств.

## Пример первого свойства компонента

```tcl
set_module_property NAME sdram_controller_altera14
```

Команда задаёт идентификатор компонента в каталоге Platform Designer. Она не переименовывает HDL-модуль в Verilog.

Это различие уже встречалось в нашей работе:

| Имя | Фактическое значение | Где используется |
| --- | --- | --- |
| Проект | `vision_core` | Файл `.qpf` |
| Ревизия | `vision_core_top` | Файл `.qsf` |
| Верхняя entity проекта | `vision_core_top` | Будущий VHDL верхнего уровня |
| Тип IP | `sdram_controller_altera14` | Свойство `NAME` в `_hw.tcl` |
| Верхний модуль IP | `RAMSYS_new_sdram_controller_0` | Объявление `module` в Verilog и `TOP_LEVEL` fileset |
| Экземпляр IP | `sdram_controller_altera14_0` | Система `memory_subsystem.qsys` |

Каждое имя имеет свою область действия. Некоторые имена можно выбирать независимо; имя верхнего HDL-модуля в fileset обязано совпасть с объявлением в исходнике.

## Карта дальнейшего разбора текущего файла

| Команда | Что будем разбирать подробно |
| --- | --- |
| `set_module_property` | Имя, версия, категория, редактируемость и свойства компонента |
| `add_fileset` | Имя набора отдельно от его типа; `QUARTUS_SYNTH`, `SIM_VERILOG`, callbacks |
| `set_fileset_property` | Верхний модуль и свойства конкретного набора файлов |
| `add_fileset_file` | Имя выходного файла, тип HDL, исходный путь, `TOP_LEVEL_FILE`; принадлежность последнему объявленному fileset |
| `add_interface` | Имя интерфейса, его тип и роль `start`/`end`; это не направление всех портов сразу |
| `set_interface_property` | Связи clock/reset, словная адресация, задержки и число незавершённых чтений |
| `add_interface_port` | Имя интерфейса, точное имя HDL-порта, роль, направление и ширина |
| `set_interface_assignment` | Метаданные интерфейса, включая `embeddedsw.configuration.isMemoryDevice` |

Относительный `PATH` в нашем компоненте рассчитан от каталога `_hw.tcl` до исходного RTL. Если переносим описание, путь нужно проверить заново. `ENABLE_RELATIVE_INCLUDE_PATHS` относится к обработке HDL include-путей и не следует считать его переключателем всех относительных путей описания.

Пустой раздел `parameters` в текущем файле означает, что настраиваемые параметры IP не объявлены. Добавить поле частоты в GUI недостаточно для изменения зафиксированных чисел в готовом Verilog. Любой будущий параметр должен иметь реализованную связь с RTL или генератором и проверенный диапазон допустимых значений.

## Как проверяем понимание и изменения

Для каждого следующего фрагмента устанавливаем:

1. Какое окружение выполняет команду и что означают её аргументы.
2. Что относится к метаданным, а что влияет на генерацию аппаратуры или адаптеров.
3. Как значение связано с реальным HDL, подключением системы и документацией IP.
4. Какой файл изменяем и какой результат ожидаем.
5. Как проверяем результат: чтение файла, загрузка каталога, валидация, генерация, симуляция или STA.

Успешная загрузка `_hw.tcl` не доказывает работу контроллера памяти. Валидация интерфейсов не заменяет симуляцию; симуляция RTL не заменяет проверку временных ограничений и измерения на плате.

Подробный разбор начат после завершения настройки и генерации через GUI. Его первая тема — **команда, аргументы и `package require -exact qsys 16.1`**. Перед разбором заново прочитать конечный `_hw.tcl`, чтобы обсуждать фактический результат, а не промежуточную версию.
