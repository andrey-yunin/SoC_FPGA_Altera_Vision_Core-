# Технический отчёт по Vision Core

## Мастер, формирователи и сборка — 2026-11-11

### Границы модулей

Система разбита на четыре узла с явными контрактами:

| Модуль | Домен такта | Задача | Входы → выходы |
| --- | --- | --- | --- |
| `reset_conditioner` | `CLOCK_50` | фильтр кнопки сброса, синхронное снятие, удержание при незалоченной PLL | `key_reset_n`, `pll_locked` → `reset_n_out` (активный низкий), `reset_req_out` (активный высокий) |
| `button_conditioner` | домен потребителя | синхронизация, антидребезг 10 мс, событие нажатия | `btn_n` → `level`, `stb` (импульс 1 такт) |
| `memory_test_master` | `memory_clk` (100 МГц) | одиночные записи/чтения по Avalon-MM, индикация | `sw`, `wr_stb`, `rd_stb` → `av_*`, `hex0..hex5` |
| `vision_core_top` | — | только соединения | — |

Принцип: мастер не знает ни про кнопки, ни про их полярность, ни про дребезг — он получает готовые события. Фильтры стоят в топе рядом с фильтром сброса, поэтому вся «приводка сигналов» видна в одном месте. Первый вариант (фильтры внутри мастера) был отвергнут именно по этой причине: мастер переставал быть чистым Avalon-MM мастером.

Тонкость по такту: фильтр сброса обязан работать до захвата PLL, поэтому он в `CLOCK_50`. Кнопочные фильтры — в `memory_clk`, потому что до захвата PLL нажимать бессмысленно, а строб должен приходить в том же домене, что автомат мастера.

### Сброс: найденный дедлок

В подсистеме `reset` заведён на `clk_0.clk_in_reset`, а `clk_0.clk_reset` идёт в `pll_0.reset` (строки 125, 411 `memory_subsystem.qsys`). Если бы в формирователе сброса участвовал `pll_locked`, получился бы замкнутый круг: сброс подсистемы держит PLL → `pll_locked = 0` → сброс не снимается никогда.

Решение: кнопка фильтруется одна (`raw <= not key_reset_n`), а `pll_locked` добавляется только на выходе для мастера:

```vhdl
reset_req_out <= req or (not pll_locked);  -- мастеру: кнопка ИЛИ PLL не залочена
reset_n_out   <= not req;                  -- подсистеме (и PLL): только кнопка
```

### Пины: источник и ограничение импорта

Номера пинов взяты не по памяти и не из сети, а из официального baseline pinout Terasic, поставляемого с Quartus:

- `quartus/common/devplatforms/DE1_SoC_Board/DE1_SoC_Board.qar`;
- распакован `quartus_sh --restore` (в архиве `DE1_SOC_golden_top.v`, `platform_setup.tcl`);
- таблица назначений — в `platform_setup.tcl` (команды `set_location_assignment`).

Перекрёстная проверка: `KEY[0] = PIN_AA14` совпало с уже используемым в проекте `RESET_N`, что подтверждает корректность источника.

Добавлено 55 назначений: `SW[0..9]`, `KEY[1..3]`, `HEX0..HEX5` (по 7 сегментов). Стандарт — `3.3-V LVCMOS`, единообразно с DRAM (Terasic в своём baseline ставит `3.3-V LVTTL`; смешивать стандарты в одном банке нежелательно).

Ограничение инструмента: импорт CSV подхватывает колонку `I/O Standard`, но колонку `Location Pin` Quartus не понимает — назначения при этом молча не применяются (`Critical Warning (169085)`). Рабочий путь — вписать `set_location_assignment` прямо в QSF и переоткрыть проект (импорт из собственного QSF Quartus запрещает).

### Предупреждения сборки и их трактовка

| Предупреждение | Трактовка |
| --- | --- |
| `HEX4[*]` stuck at VCC | Норма: `hex4 = "1111111"`, сегменты активны низко, разряд погашен |
| `DRAM_BA[0..1]` stuck at GND | Законно для ручного режима: `TEST_BASE = 0x1F0000`, SW двигает только биты [9:0] → `addr[24] = 0`, `addr[10] = 0`, банк всегда 00 |
| `DRAM_CKE` stuck at VCC | В RTL контроллера `clk_en = 1'b1`, `zs_cke = clk_en` — структурная константа |
| `DRAM_DQM[0..1]` stuck at GND | Мастер всегда ставит `byteenable_n = "00"` → DQM = 00; байтовые маски будут проверяться в автотесте L5 |
| `KEY[3]` не управляет логикой | Порт объявлен как `(3 downto 1)`, используются только `KEY[1]` и `KEY[2]` |
| 176250/176251 fast I/O registers | Wildcard-назначения vendor-контроллера, присутствовали и до интеграции |
| 12125 reset_conditioner не в проекте | Устранено добавлением файла в проект |

### Ограничения ручного режима

Поскольку `TEST_BASE = 0x1F0000`, а SW подаётся только на младшие 10 бит адреса, тест работает в одном месте памяти: банк 0, строка 62, колонки 0…1023. Ни строки, ни банки, ни границы страниц ручной режим не проверяет — это задача автотестов L2/L3.

### Не проверено

- Прошивка и работа на плате: запись/чтение кнопками не запускались.
- Функциональная симуляция: тестбенчей нет, модель микросхемы памяти не подключена.
- `DRAM_CLK` как отдельные часы в SDC не ограничен; I/O sign-off SDRAM по-прежнему открыт.

## Тестовый Avalon-MM мастер — 2026-11-10

Первый собственный мастер для slave-порта SDRAM-контроллера. Файл `fpga/memory_test_master.vhd`, на VHDL, в домене `memory_clk` (= `sdram_access_clk_clk`, 100 МГц). Platform Designer не менялся: все нужные порты (`sdram_access_*`) уже выведены наружу, в топе они до сих пор заглушены константами.

**Зачем.** Без мастера контроллер не выполняет ни одной транзакции: BA/CKE/DQM помечаются stuck at VCC/GND, и отчёт STA подписывает только внутреннюю логику, а не SDRAM I/O. Мастер с известным шаблоном данных даёт реальные переключения на `DRAM_*` и позволяет получить честные setup/hold.

**Протокол slave-порта (проверено по RTL):** `wr = (~az_wr_n | ~az_rd_n) & !za_waitrequest` — запись во входной FIFO уровне-чувствительна каждый такт, поэтому запрос обязан сниматься на следующем такте после того, как `waitrequest` стал 0, иначе слово попадёт в очередь дважды. `az_cs` объявлен, но нигде не используется — `chipselect` держится в 0. При чтении маска принудительно заменяется на `2'b0` (DQM = 00). Адрес — номер слова (25 бит), `byteenable_n` — активный низкий. Ответы чтения приходят импульсом `readdatavalid` без адреса, в порядке запросов, до 7 в полёте.

**Решения:**
- Ручной режим: `KEY[1]` — запись одного слова, `KEY[2]` — чтение того же адреса. `KEY[0]` занят под `RESET_N` (пин AA14). Автотест L0–L5 отложен.
- Кнопки обрабатываются в полярности пина (1 = отпущена, 0 = нажата), без инверсии; порты `btn_write_n` / `btn_read_n`. Внутри — два триггера синхронизации (защита от метастабильности) и счётчик антидребезга на 10 мс (`DB_MAX` = 1 000 000 тактов); на подтверждённое нажатие формируется импульс `btn_w_stb` / `btn_r_stb` длиной ровно один такт.
- Сброс: `reset_req` активный высокий, асинхронная установка и синхронное снятие через 2 каскада (`rst_sync`), наружу — `rst`. В топе предполагается `reset_req <= (not RESET_N) or (not pll_locked)`.
- Адрес: `TEST_BASE(24:10) & SW[9:0]`, `TEST_BASE` = `0x1F0000` (регион 0x1F0000…0x1F03FF), чтобы не пересекаться с будущими буферами кадров, растущими с нуля.
- Данные записи — константа `x"A5A5"`, `byteenable_n = "00"`.
- Индикация только на HEX: `HEX3…HEX0` — слово, `HEX5` — код состояния (0 простой, 1 запись, 2 чтение, E таймаут, погашен при старте), `HEX4` погашен. LEDR не используются — на 10 диодах 16-битное слово всё равно не видно.

**Автомат:** `S_IDLE → S_WR` (запрос `write_n = 0` висит до `waitrequest = 0`, затем снимается) и `S_IDLE → S_RD_REQ → S_RD_WAIT` (после приёма запроса ждём `readdatavalid`; если его нет за `TMO_MAX` = 65535 тактов = 655 мкс, состояние становится `E`). Запросы выдаются регистрами, поэтому при `waitrequest = 1` уровень просто удерживается.

**Не проверено:** файл не компилировался — в среде нет Quartus и GHDL; модуль не инстанцирован в `vision_core_top.vhd`, не добавлен в проект, пины `HEX*` и `KEY[1:2]` не назначены (номеров в репозитории нет — брать из DE1-SoC User Manual). Симуляция не выполнялась.

## Точка остановки — 2026-11-09, вечер: 100 МГц и разбор тайминга

Полная компиляция на 141.428571 МГц дала setup slack −2.612 нс (TNS −80.758) и Fmax 103.28 МГц (Slow 1100 mV 85 °C). Худшие 10 путей — `oe`/`oe~_Duplicate_*` → `DRAM_DQ[*]`, slack −2.612…−2.491 нс. Причина: Fitter игнорирует `FAST_OUTPUT_ENABLE_REGISTER=ON` на `oe`, регистр остаётся в core и дублируется на 16 линий DQ; `FAST_OUTPUT_REGISTER` на `m_data` применён. Это внутренний путь, не SDRAM I/O.

Решение: 100 МГц. В Platform Designer оба выхода `pll_0` = 100.0 МГц; в `RAMSYS_new_sdram_controller_0.v` refresh reload `1103 → 780` (781 такт × 10 нс = 7.81 мкс ≤ 64 мс/8192 = 7.8125 мкс); `14143` не менялся. SDC не менялся: `derive_pll_clocks` даёт `divclk` 10.000 нс. Это единственная правка вендорного RTL; исходный файл сохранён в коммите deaea28, SHA-256 исходника 4bda493fa7c3ed07fb9ff7c93d5dae88c2154d698195848c53aedea67b337e9f.

Результат (2026-11-09 15:29): setup +0.418 нс (TNS 0), hold Slow 85 °C +0.189 нс (худший угол Fast 0 °C +0.077), recovery +6.530, removal Slow 85 °C +0.403 (худший угол +0.198), pulse width положительный, Fmax 104.36 МГц (0 °C 106.28). Critical Warning 332148 отсутствует. Ресурсы: 69 ALM, 114 регистров, 41 пин, 1 PLL.

Остаточные риски: hold/removal в худших углах 0.077/0.198 нс — мало для продакшена; `oe` fast output enable всё ещё игнорируется; `DRAM_CLK` — единственный неограниченный выход; BA/CKE/DQM stuck at VCC/GND, потому что Avalon-MM master не подключён, транзакций нет. Это не подпись SDRAM I/O. Следующий шаг — полный путь, затем master/test pattern и повторный STA.

## Проверка железа и таймингов SDRAM — 2026-11-09 (история до перехода на 100 МГц)

Плата DE1-SoC у пользователя, работа возобновлена. Пункт 1 плана от 2026-11-06 выполнен по микросхеме памяти; ревизия PCB ещё не установлена.

**Подтверждено с платы:**
- маркировка SDRAM: `IS42S16320D-7TL` — ISSI, 512 Mbit, организация 32M×16, 4 банка, 3.3 В LVTTL, TSOP-II 54, скоростной суффикс `-7`;
- официальный даташит: `docs/42-45R-S_86400D-16320D-32160D.pdf`, семья IS42/45R86400D/16320D/32160D и S-варианты, Rev. B1 02/14/2025, 66 с.;
- строка `SoC-001-14791` — внутренний номер/серийник Terasic, не ревизия. Ревизия PCB (`REV. ...`) ещё не найдена; на тайминги не влияет, нужна для сверки user manual и схемы.

**Тайминги `-7` при CL3 и частоте 141.428571 МГц (tCK = 7.071 нс).** Частота чипа 143 МГц соответствует tCK min = 7.0 нс, то есть 142.857 МГц; запас нашего периода +0.071 нс (около 1.0 %). CL2 при нашей частоте недопустим (tCK2 min = 7.5 нс), обязателен CL3.

**Частота — выбранная рабочая точка, а не константа.** 141.428571 МГц взяты из донорского RTL, когда тип установленной памяти ещё не был подтверждён. После сверки с `IS42S16320D-7TL` частота проверена и оставлена: она попадает в узкое окно, заданное двумя жёсткими ограничениями. Сверху: tCK3 min = 7.0 нс → f ≤ 142.857 МГц. Снизу: зашитый в RTL reload счётчика refresh 1103 (период 1104 такта) должен укладываться в 64 мс / 8192 = 7.8125 мкс → f ≥ 1104 / 7.8125 мкс = 141.312 МГц. Допустимое окно — 141.312…142.857 МГц (около 1.09 %). Наши 141.428571 МГц стоят у нижней границы: запас по tCK +0.071 нс (1.0 %), интервал refresh 7.806 мкс против 7.8125 мкс (запас 6.5 нс, 0.08 %). Это точка вблизи нижней границы: запас по tCK близок к максимальному при ещё выполнимом refresh. Понизить частоту для большего запаса по tCK нельзя без правки вендорного RTL (константа 1103); повышать нельзя из-за tCK min. Решение осознанное, не предположение.

Входные параметры заданы при времени фронта tt = 1 нс; при более медленном фронте добавляется (tt/2 − 0.5) нс. Для записи использовать tDS = 1.5 нс и tDH = 0.8 нс; типовые значения не подставлять.

**Проверка контроллера по даташиту.** `RAMSYS_new_sdram_controller_0.v` не параметризован, геометрия зашита: `az_addr[24:0]` — 25-битный словный адрес, `zs_addr[12:0]` — 13 бит строки (8192), `zs_ba[1:0]` — 4 банка, `zs_dq[15:0]` и `zs_dqm[1:0]` — 16 бит. 2^25 слов × 2 байта = 64 МиБ = 512 Mbit, что совпадает с `IS42S16320D`. Карта адресов: банк = {addr[24], addr[10]}, строка = addr[23:11], колонка = addr[9:0]; при CAS-команде A12–A10 принудительно 0 (auto-precharge не используется, precharge явный). Инициализация пишет mode register `{{3{1'b0}},1'b0,2'b00,3'h3,4'h0}`: CL3, burst length 1, sequential, standard; A9 = 0. Счётчик refresh: 14143 после сброса (около 100 мкс), затем перезагрузка 1103, период 1104 такта = 7.806 мкс, что соответствует 64 мс / 8192 при нашей частоте. CL3 подтверждён `rd_valid[2]`, tRCD/tRP = 3, tRC = 9. Вывод: контроллер согласован с `-7` на 141.428571 МГц, правки RTL под даташит не требуются.

**Риск чтения.** В контроллере `za_data <= zs_dq;` — данные защёлкиваются прямо на такте контроллера, без IDDR, input delay и фазовой подстройки. Запас чтения целиком определяется фазой PLL между `outclk0` (контроллер) и `outclk1` (`DRAM_CLK`) и задержками платы. При фазе 0° грубая оценка: setup ≈ 7.071 − 5.4 = 1.671 нс до вычета входного setup FPGA, перекоса часов и платы; hold ≈ tOH = 2.7 нс. Эти числа не являются доказательством: точный расчёт с min/max и задержками платы — пункты 4–5 плана. Донорские −52° без такого расчёта не применять.

**Состояние ограничений.** `fpga/vision_core_top.sdc` создан и добавлен в проект; в QSF есть `set_global_assignment -name SDC_FILE vision_core_top.sdc`. В SDC только базовый слой: `create_clock -name CLOCK_50 -period 20.000`, `derive_pll_clocks`, `derive_clock_uncertainty`. Автоматический SDC есть только у `altera_reset_controller` (два false_path на цепочки синхронизатора сброса) — не дублировать. У PLL авто-SDC нет, но `derive_pll_clocks` корректно построил производные часы. Назначение `CLOCK_50` в QSF задаёт только пин `PIN_AF14` и `3.3-V LVCMOS`; период задан в SDC.

## Универсальная платформа и прикладные сценарии

Уточнение пользователя 2026-11-05: одна аппаратная платформа должна применяться к разным объектам и задачам. Сегодня — размеры и повреждения яблок; другой сценарий — количество предметов в кадре; третий — число точек на гранях игровых костей. Поэтому готовая категория, понятия «яблоко», «гниль», «спичка» или «значение кости» не должны определять универсальные IP-ядер и аппаратную схему.

Граница ответственности: FPGA исполняет выбранные математические операции и выдаёт данные в описанном формате; приложение на ARM задаёт сценарий и трактует результат. Нейтральные операции FPGA могут включать фильтрацию, преобразование формата, маски, границы, связные области и числовые статистики. Выделение по порогу — операция, а не заключение о наличии повреждения. Ранее употреблявшиеся «подозрительные области/дефекты» на выходе FPGA читать как нейтральные области, выделенные выбранной цепочкой; их прикладной смысл определяется ARM.

Не фиксировать единственный выход FPGA только в виде списка объектов: в зависимости от выбранной цепочки результатом могут быть изображение, маска, области/контуры или характеристики. Считать числовые величины аппаратно допустимо; например число связных компонент является нейтральным результатом. Вывод «столько яблок» или «столько точек на конкретной кости» требует прикладного сопоставления. Объединение перекрывающихся объектов, пропуски и помехи требуют проверки конкретного сценария.

| Сценарий | Возможная универсальная подготовка FPGA | Прикладное решение ARM |
| --- | --- | --- |
| Яблоки | Подготовленное изображение, маски/области, характеристики | Размерная категория, оценка повреждений и качества |
| Подсчёт предметов | Маски, области, положение, площадь и форма | Какие области считать целевыми предметами и итоговое количество |
| Игровые кости | Маски/области и характеристики границ/точек | Выделение костей, привязка точек к каждой видимой грани и значение |

Это варианты разделения, не доказательство достаточности одного алгоритма для всех сцен. Универсальность достигается повторным использованием IP и сменой конфигурации/ПО; она не означает одинаковые пороги, оптику, свет или неизменяемую цепочку для всех объектов. Прикладную интерпретацию сохранять в ARM; частные ускорители допускаются позднее по явному обоснованию, а не как исходная обязательная специализация FPGA.

## Общая схема от камеры до результата

Актуальная концепция после согласования корректировок 2026-11-05: обработчик получает согласованный поток либо от приёмника камеры, либо из SDRAM через DMA. Локальные IP соединяются напрямую, без обязательного кадрового прохода между ними. Выбор источника, запись/разветвление потока и политики задержек детализируются отдельно.

```text
Камера → приёмник/подготовка ──────────┐
                                     ├→ выбранный источник → составной IP → результат
SDRAM → контроллер → DMA чтения ──────┘                     (внутри FIFO и цепочка IP)

Сохранение входного изображения и/или результата:
поток → DMA записи → контроллер → FPGA SDRAM

Готовые данные → защищённый интерфейс обмена → HPS
```

Изображения/маски могут сохраняться через DMA, записи характеристик — передаваться через выбранную очередь/интерфейс. Состав выхода зависит от цепочки. Если одновременно работают обработка и сохранение, разветвление потока обязано иметь определённую политику готовности и потерь; на схеме оно показано функционально, не как уже реализованный узел. Автономность FPGA и отдельная роль HPS сохраняются.

### Развёрнутый пример кадрового режима

Сводная запись от 2026-11-05 по запросу пользователя. Схема ниже полностью раскрывает обсуждаемый вариант с сохранением кадра перед обработкой. Подтверждены автономность FPGA, разделение обязанностей с HPS, формат RAW12 в uint16_t и границы IP с внутренними FIFO и внешними DMA. Конкретная камера, контроллер/тип DMA, параметры буферов, алгоритм, интерфейс HPS и производительность пока не утверждены. Предыдущая общая схема ниже остаётся ранним обзором; при чтении текущего обсуждения использовать этот раздел и раздел согласованных границ IP.

```text
Камера: RAW + PCLK + сигналы строки/кадра
    ↓
Приёмник камеры: захват, проверка строк/кадров
    ↓
Формирование 16-битных слов и кадровых метаданных
    ↓
FIFO захвата / переход тактового домена при необходимости
    ↓
DMA записи входного кадра
    ↓
Общий контроллер SDRAM с арбитражем
    ↓
Входной кадровый буфер в FPGA SDRAM
    ↓ чтение через тот же контроллер SDRAM
DMA чтения кадра
    ↓ Avalon-ST
┌─ IP обработчика ──────────────────────┐
│ Входной FIFO                          │
│     ↓                                │
│ Подготовка пикселей для алгоритма     │
│     ↓                                │
│ Буферы строк / формирователь окна    │
│     ↓                                │
│ Вычислительный конвейер               │
│     ↓                                │
│ Выходной FIFO                         │
└──────────────────────────────────────┘
    ↓ Avalon-ST
DMA записи результата
    ↓ тот же контроллер SDRAM
Выходной буфер в FPGA SDRAM
    ↓ публикация завершённого результата
Предложенный интерфейс обмена с HPS:
регистры/описание результата + защищённое окно данных + IRQ
    ↓
HPS: собственные задачи анализа и категоризации
```

Контроллер внешней SDRAM один; повторы на схеме обозначают обращения к нему в разных фазах. Входной и выходной буферы — разные адресные области одной FPGA SDRAM. DMA чтения и обе роли DMA записи представлены функционально; число экземпляров/каналов mSGDMA и возможность их совместного использования ещё выбрать.

Системный аппаратный автомат FPGA настраивает камеру, выдаёт задания DMA, переключает буферы, контролирует число пикселей и ошибки. Контроллер SDRAM аппаратно выполняет инициализацию и refresh. Начальный запуск/задания FPGA не зависят от программного обслуживания HPS. Публикация буфера выполняется после подтверждённого завершения записи и проверки кадра. Механизм готовности и политика потерь ещё подлежат детализации.

FIFO захвата и входной FIFO обработчика — разные очереди: первая сглаживает запись камеры в память и при необходимости выполняет CDC; вторая входит в IP и согласует поток DMA чтения с вычислением. Это не три копии целого кадра во внутренних FIFO. Метки и метаданные сохраняются согласованно, их представление ещё не выбрано. RAW12 хранится в младших битах uint16_t; регистры/маркеры не помещаются в старшие четыре бита пикселя.

Схема не утверждает конкретный фильтр. Пример буферов строк относится к локальной оконной обработке; Bayer и Mono требуют различимой подготовки. Вариант обработки на входном потоке до записи кадра остаётся альтернативой для оптимизации, его нельзя смешивать с показанным порядком без явного изменения схемы.

Для этого полного кадрового прохода при примере 1280×800, 16 бит, 60 FPS: запись исходника 122,88 МБ/с + чтение исходника 122,88 МБ/с + запись полноразмерного 16-битного результата 122,88 МБ/с = 368,64 МБ/с полезного трафика, без чтения HPS и накладных расходов. Достижимость на FPGA SDRAM не подтверждена. Пример нужен для последовательного разбора узлов; заявлять 60 FPS для такого тракта до расчёта/измерения нельзя.

## Предварительная блоковая схема ПЛИС

Обсуждение от 2026-11-05, без кода. Схема предложена для неподвижного стенда; окончательный состав фильтров и граница ПЛИС/ARM не утверждены. Генератор VGA-развёртки есть у пользователя; исходники и интерфейс ещё не изучены.

Основной тракт: камера RAW → приёмник интерфейса → нормализация потока и переход тактового домена при необходимости → подготовка пикселей → фильтрация → выделение масок объекта и кандидатов в дефект → накопление характеристик → передача результатов ARM. Обработка локальных окон требует строковых буферов. Для цветного Bayer способ получения яркости/цвета выбирается явно: значения мозаики не считаются готовым серым изображением.

Потоковое выделение связных компонент и накопление площади, сумм координат, границ и признаков рассматриваются как аппаратные кандидаты. Сложность объединения меток и требуемая память оцениваются отдельно. Полная топология контуров, интерпретация подозрительных областей, классификация и пересчёт в физические единицы предварительно относятся к ARM; это предложение по распределению, не готовое решение.

Параллельная ветка отладки: выбранное изображение/маска → запись в кадровую память → чтение в темпе VGA → подготовка изображения и отметок → выход на монитор. Пользовательский генератор развёртки задаёт время вывода; остальные блоки не предполагаются уже реализованными. Число буферов и конкретная память выбираются по скоростям и требованию отсутствия разрывов кадра. Отображение не должно останавливать основной тракт.

Отдельный путь сохранения исходных/подготовленных пикселей позволяет передавать ARM участки изображения или кадр, если они нужны выбранному алгоритму. Область интереса может стать известна только после прохождения её пикселей; поэтому ретроспективное извлечение требует хранения или иной заранее определённой схемы. Минимизация передачи не равнозначна запрету кадровой памяти.

Управление: ARM задаёт регистры камеры и обработки через выбранные интерфейсы; отдельная логика обеспечивает триггер/синхронизацию. Контроль тракта включает номера кадров, временные метки, счётчики переполнений и ошибок. FIFO не компенсирует постоянный недостаток пропускной способности; возможность остановить камеру не предполагается. Параметры обработки следует согласованно применять на границе кадра.

## Рабочая архитектура для обсуждения

Предлагаемый логический тракт: источник пикселей → коррекция и фильтрация → выделение объектов и признаков → измерения → категоризация. Его распределение между ПЛИС и ARM остаётся открытым.

Без камеры возможна подача сохранённого изображения из памяти в ПЛИС с воспроизведением пиксельного потока. После подключения камеры источник меняется, но условия потока и синхронизации должны быть определены явно. Наличие конкретного загрузчика, драйвера или аппаратного интерфейса пока не предполагается.

Постоянная передача полного обработанного кадра на ARM не принята как обязательная архитектура. Кандидаты для обмена — характеристики объектов, координаты, признаки и нужные участки изображения. Полный кадр может потребоваться для отладки или отдельных алгоритмов; необходимость кадрового хранения устанавливается анализом зависимостей, а не запрещается заранее.

Также не принимаем раннюю потерю информации: одна карта границ может оказаться недостаточной для различения повреждений, окраски, бликов и теней. Какие исходные яркостные или цветовые данные сохранять, решается по экспериментам.

## Фильтры и контуры

Перечень ниже — кандидаты для исследования, а не утверждённый конвейер.

### Внешняя геометрия

Для выделения яблока рассматриваются подавление шума, отделение от фона, морфология, выделение связных компонент и внешних границ. В контролируемых условиях пороговая обработка может стать базовым методом; её пригодность нужно проверить на выбранном фоне и освещении.

Заполненная маска объекта, тонкая карта границ и исходное изображение имеют разные назначения. Площадь можно считать по маске; измерение площади через геометрический контур требует явного определения метода и сравнения результатов. Соприкасающиеся и обрезанные границей кадра объекты требуют отдельной политики обработки.

### Внутренние области

Внутри маски исследуются градиенты, например Sobel, пороговая обработка, объединение границ, контуры и их вложенность. Кандидаты в дефект могут фильтроваться по площади, форме, контрасту и положению. Фильтр только по площади не отличает повреждение от блика или естественного рисунка кожицы.

Замкнутый внутренний контур не доказывает гниль. Слабоконтрастная вмятина может не образовать такой контур. Толщина линий на карте границ также влияет на полученную иерархию. Классификация дефекта требует проверки по размеченным исходным изображениям.

### Потоковая реализация

Для локальных фильтров, градиентов и морфологии рассматриваем оконную обработку со строковыми буферами. Для каждой операции необходимо определить размер окна, правила границ, диапазоны промежуточных значений, разрядность, производительность и задержку.

Связные компоненты, контуры и их иерархия имеют зависимости, выходящие за локальное окно. Потоковое выделение компонент возможно рассматривать отдельно, но оно требует учёта меток и их эквивалентности; завершённость объекта может стать известна позднее его первых пикселей. Конкретная реализация и ресурсы ещё не оценивались. Предложение оставить иерархию контуров ARM также не утверждено.

## Граница автономной ПЛИС и HPS по памяти

Указание пользователя 2026-11-05: у HPS собственные задачи; не привлекать его к управлению работой ПЛИС. Захват, подготовка потока, буферизация, выдача заданий DMA и смена аппаратных буферов должны выполняться без программного обслуживания ARM. Наличие HPS само по себе не является основанием переносить на него настройку каждого переноса.

Прежняя рекомендация mSGDMA → DDR3 HPS с ARM-дескрипторами снята как основной вариант: она не соответствует выбранной границе автономности. Для автономного кадрового тракта предлагается использовать внешнюю SDRAM 64 МБ, физически подключённую к FPGA. DDR3 1 ГБ остаётся памятью задач HPS. Наличие обеих памятей подтверждено [спецификацией DE1-SoC Terasic](https://www.terasic.com.cn/cgi-bin/page/archive.pl?CategoryNo=167&Language=English&No=836&PartNo=2). Конкретный контроллер SDRAM, версия инструментов и пропускная способность ещё не проверены.

Предлагаемый тракт: приёмник камеры → FIFO → DMA/аппаратный writer → контроллер SDRAM в FPGA → внешняя SDRAM FPGA. Аппаратный автомат задаёт адрес и длину, управляет готовностью буферов, отслеживает ошибки и завершение передачи. При использовании mSGDMA автомат должен выдавать предусмотренные IP задания и обрабатывать ответы; сам IP без этих заданий не предполагается автономным. Возможен собственный burst writer; выбор между ним и mSGDMA открыт. Инициализация камеры, тактирование, сброс и инициализация SDRAM также должны укладываться в выбранную автономность.

Граница с HPS проходит по завершённым данным и явно заданному интерфейсу. FPGA публикует дескриптор результата/буфера: идентификатор кадра, доступность, формат, размер, шаг строки и статус. HPS читает опубликованные данные через согласованный интерфейс либо получает их копию в свою DDR3. Прямой самостоятельный доступ ARM к FPGA SDRAM не предполагается готовым: требуются окно памяти или аппаратный канал обмена, адресная карта и арбитраж.

Предлагается разделение прав: рабочие кадровые буферы и их запись принадлежат FPGA; опубликованный буфер защищается от перезаписи на время передачи/чтения. Запрос и освобождение результата со стороны HPS относятся к интерфейсу обмена, а не к программированию захвата и DMA. При задержке HPS аппаратный тракт должен следовать заранее выбранной политике: очередь, пропуск новых результатов/кадров или иное ограниченное поведение. Бесконечно сохранять все кадры при конечной памяти и остановившемся потребителе невозможно. Арбитраж должен учитывать гарантированный темп захвата.

Согласованный RAW12 в uint16_t, младшие 12 бит и little-endian сохраняются независимо от выбора памяти. Два или более кадровых буфера и конкретная политика владения ещё требуют выбора. Для примера 1280×800 два буфера занимают 4 096 000 байт; это оценка ёмкости, не доказательство достаточной пропускной способности.

Источники по аппаратным вариантам: [mSGDMA User Guide](https://docs.altera.com/r/docs/683130/26.1/embedded-peripherals-ip-user-guide/modular-scatter-gather-dma-core?contentId=ObgE4HydMdnczdfc0Of4Lg). Дополнительный soft-core в FPGA не требуется; управляющие автоматы являются аппаратной логикой.

Основа архитектуры предложена пользователем: автономная FPGA, собственные задачи HPS, чёткая граница обмена по памяти и завершённым данным. Ассистент подтвердил, что его последующее описание не является иной архитектурой. Уточнение зафиксировано по поручению пользователя 2026-11-05.

Для хранения предложено три кадровых слота: заполняемый, опубликованный потребителю, свободный резерв. При размере примера 2 048 000 байт это 6 144 000 байт. Состояния и владение ведёт аппаратный автомат. FPGA публикует завершённый слот, HPS запрашивает/освобождает данные через отдельный интерфейс; освобождение потребителем не является командой захвату. При исчерпании свободных слотов не допускается перезапись удерживаемых данных: пропуск сохранения очередного кадра фиксируется аппаратно. Непрерывность потоковой обработки и сохранение каждого кадра являются разными требованиями.

Для характеристик объектов и статуса предлагается отдельная небольшая очередь/dual-port RAM с доступом HPS. Для кадров или участков — отдельный канал чтения защищённых слотов с ограниченной полосой и арбитражем. Передача всех кадров ARM не является основным режимом, но может потребоваться алгоритму или отладке; это нужно определить явно. Полноценная классификация дефектов только по числовым признакам не обещается.

Обязательная проверка до выбора FPS: для примера 1280×800, 16 бит, 60 FPS запись составляет 122,88 МБ/с; дополнительное чтение каждого кадра даёт суммарно 245,76 МБ/с полезного трафика без учёта накладных расходов. Способность внешней 16-битной SDRAM обеспечить это не подтверждена. Поэтому цикл «записать весь кадр → прочитать ради каждого локального фильтра» не предлагается как основной. Проверить реальный временной бюджет SDRAM с учётом refresh, burst, переключений чтение/запись и конкурирующих потребителей. При нехватке полосы пересматривать FPS, число проходов, объём сохраняемых данных или аппаратную платформу явно.

Ближайший технический разбор — FIFO → mSGDMA → контроллер FPGA SDRAM: готовность, перенос слов, аппаратная выдача дескриптора, завершение и обработка переполнений. Размер/ширина FIFO, частоты, burst и число слотов пока не утверждены.

## Предложенный интерфейс FPGA и HPS

По запросу пользователя предлагаются встроенные мосты Cyclone V, без внешнего UART/SPI между частями SoC. Это конкретизация автономной архитектуры пользователя, не утверждённая реализация.

1. Lightweight HPS-to-FPGA, 32 бита: регистры состояния/ошибок и числа готовых результатов, доступ к небольшим дескрипторам, получение и освобождение опубликованного буфера. Настройки DMA захвата и рабочие буферы не экспортируются как управляющие регистры HPS.
2. Полный HPS-to-FPGA: предлагается 64-битная конфигурация как кандидат для окна чтения кадров/участков в FPGA SDRAM. Физический мост AXI подключается через interconnect Platform Designer к выбранному Avalon-MM интерфейсу контроллера/защитного окна. Ширина 64 бита не гарантирует соответствующую полезную скорость; тактирование и арбитраж требуют расчёта. Вход записи HPS в кадровую область должен отклоняться/не предоставляться аппаратным интерфейсом, а не только соглашением ПО.
3. FPGA-to-HPS IRQ: уведомление об очереди результатов или ошибке. IRQ не переносит данные и не заменяет очередь и идентификаторы кадров. Число IRQ и номера в Linux пока не назначаются.

Направление названия HPS-to-FPGA указывает инициатора транзакции: ARM отправляет адрес чтения в FPGA и получает ответ с данными по тому же мосту. Для такого чтения отдельный мост FPGA-to-HPS не нужен. DDR3 HPS по-прежнему принадлежит задачам ARM; FPGA не пишет туда кадры основного захвата.

Предлагаемая транзакция обмена: FPGA завершает запись и публикует целостный дескриптор → сигнализирует IRQ → HPS атомарно получает/закрепляет дескриптор → читает результат/изображение через защищённое окно → освобождает по идентификатору кадра и слота. Дескриптор содержит как минимум идентификатор кадра/слота, смещение в окне, длину, формат, размеры, шаг строки и статус. Конкретный регистровый интерфейс атомарного получения ещё разработать. На период публикации/чтения данные не перезаписываются.

Доступ HPS к SDRAM арбитрируется с аппаратными потребителями и ограничивается по полосе, чтобы не нарушить захват. При задержке или отсутствии HPS аппаратная часть продолжает работу по согласуемой политике исчерпания буферов. Освобождение опубликованного буфера — взаимодействие с потребителем, а не программное управление последовательностью захвата. Начальная инициализация мостов на стороне HPS нужна для самого обмена и не должна быть условием работы FPGA тракта.

Источники: [Cyclone V HPS-to-FPGA и lightweight bridges](https://docs.altera.com/r/docs/683126/21.2/cyclone-v-hard-processor-system-technical-reference-manual/hps-to-fpga-and-lightweight-hps-to-fpga-bridges?contentId=~nn50kFKs2zDCenAK1bFmQ), [Cyclone V HPS TRM](https://www.intel.com/programmable/technical-pdfs/683126.pdf). ## Согласованные границы IP обработчика

Зафиксировано по прямому поручению пользователя 2026-11-05: входной и выходной FIFO входят в IP обработчика. DMA чтения, DMA записи и контроллер SDRAM являются внешними системными компонентами. Вход и выход IP — потоковые интерфейсы Avalon-ST. Процессор внутри IP не требуется.

Схема обсуждённого тракта обработки сохранённого кадра:

```text
Кадровый буфер SDRAM
        ↓ через контроллер SDRAM
DMA чтения
        ↓ Avalon-ST
┌─ IP обработчика ──────────────────────┐
│ Входной FIFO                          │
│     ↓                                │
│ Локальные буферы / окно при нужде     │
│     ↓                                │
│ Вычислительный конвейер               │
│     ↓                                │
│ Выходной FIFO                         │
└──────────────────────────────────────┘
        ↓ Avalon-ST
DMA записи результата
        ↓ через тот же контроллер SDRAM
Отдельный выходной буфер SDRAM
```

Чтение и запись обращаются к общему контроллеру SDRAM с арбитражем. Показанная последовательность описывает обработку сохранённого кадра; необходимость всех полных проходов и достижимый FPS ещё проверяются. Она не отменяет возможности подключить потоковый вход IP к другому согласованному источнику, включая камеру после подготовки данных.

IP управляет своими FIFO и согласует готовность входа/выхода. DMA чтения получает адрес и длину от системного аппаратного автомата; вычислительное ядро IP не адресует SDRAM. На выходе DMA записи размещает результаты по адресам, заданным аппаратной логикой системы. Конкретные параметры и наличие дополнительных внутренних буферов в готовом DMA не предполагаются заранее; не дублировать их без расчёта.

Полный кадр внутри IP не хранится по умолчанию. Для предложенного локального фильтра 3×3 нужны буферы строк и регистры окна; алгоритм и правило границ ещё не выбраны. Подготовка Mono/Bayer рассматривается отдельно. Размеры, разрядность и такты FIFO, глубина конвейера, конкретные роли сигналов, readyLatency/readyAllowance и передача границ строк/кадра ещё не утверждены. Все данные и метаданные должны согласованно проходить паузы и задержки.

Следующий разбор — входной Avalon-ST и приём данных во внутренний FIFO IP: какие сигналы, по какому такту и при каком условии происходит передача. Обсуждение остаётся без кода; исходники IP не созданы.

## Модульный конструктор обработки

Пользователь уточнил и подтвердил концепцию 2026-11-05: каждое ядро фильтрации или иной операции — самостоятельный IP-компонент с собственным интерфейсом, возможностью отдельной проверки и повторного использования. Цепочка собирается подключением совместимых IP-компонентов. Обработчик может оформляться как составной IP-компонент, объединяющий выбранные ядра и их соединения с общими входным/выходным FIFO. Составной обработчик является уровнем интеграции; самостоятельность входящих IP-ядер сохраняется. Конкретный набор ядер пока не выбран.

Предлагаемая организация оболочки: входной Avalon-ST → входной FIFO → выбранная цепочка ядер → выходной FIFO → выходной Avalon-ST. DMA и контроллер SDRAM остаются внешними. Между совместимыми потоковыми ядрами не требуется полный проход через SDRAM после каждой операции. Локальные строки и окна размещаются там, где нужны алгоритму; не добавлять отдельные FIFO автоматически к каждому ядру без расчёта.

Примеры альтернативных цепочек после необходимой подготовки пикселей: сглаживание → порог → морфология; сглаживание → градиент → порог; коррекция изображения → накопление статистики. Это иллюстрации конструктора, не выбранные алгоритмы распознавания дефектов.

Единый механизм Avalon-ST — необходимая, но недостаточная совместимость. Для каждого ядра определить формат данных, разрядность, организацию пикселей, границы строк/кадров, правила пауз, задержку и геометрию выхода. Маску нельзя автоматически подменять RAW-изображением, Bayer — монохромным изображением. Ядра, выдающие характеристики объектов вместо пикселей, имеют отдельный тип результата. Несовместимые форматы требуют явного адаптера. Метаданные и состояние окон продвигаются согласованно с принятыми данными.

Пользователь предложил программный выбор комбинаций из приложения, связанного с ARM. Это расширяет конструктор выбором заранее реализованных ядер и маршрутов во время работы. Конкретный набор ядер, допустимые комбинации и детальный интерфейс ещё предстоит выбрать. Частичная реконфигурация FPGA не требуется для переключения уже синтезированных маршрутов и не поручена. Добавление отсутствующего аппаратного ядра требует изменения HW-проекта и пересборки.

## Программный выбор цепочки обработки

Статус после уточнения пользователя 2026-11-05: идея сохранена как направление развития, обсуждение конкретного переключения отложено. Приведённые ниже bypass, стадии, теневые регистры и протокол применения — предложения ассистента, не утверждённые решения.

Концептуальное расширение пользователя 2026-11-05: приложение через ARM выбирает комбинации самостоятельных IP-ядер. Способ подключения самого приложения к ARM ещё не выбран. Предлагаемый путь настройки: приложение → ПО HPS → lightweight HPS-to-FPGA → регистры конфигурации составного обработчика. Настройка маршрута не означает программного обслуживания пикселей, DMA или смены кадровых буферов: исполнение остаётся автономным в FPGA.

Предлагается начать с ограниченного числа стадий с выбором ядра и обходом bypass, а не с произвольной коммутации всех выходов со всеми входами. Пример стадий после подготовки пикселей: выбор сглаживания/обход → градиент/обход → порог/обход. Примеры профилей: сглаживание; сглаживание+градиент; сглаживание+порог; сглаживание+градиент+порог. Это предложения для последующей детализации, не утверждённые алгоритмы обнаружения повреждений.

Только присутствующие в конфигурации FPGA ядра могут включаться переключением маршрута; их логика занимает ресурсы и при обходе. Регистры могут задавать разрешение стадий, поддерживаемые коэффициенты и пороги, но возможность менять размер окна и другие параметры зависит от реализации IP. Поддерживаемые комбинации должны учитывать тип данных, разрядность, геометрию и требуемые адаптеры.

Безопасное применение предлагается транзакционным: HPS записывает теневой набор параметров и запрос применения; аппаратный автомат завершает предыдущий кадр и освобождает/согласует состояние конвейера, затем применяет настройки перед следующим кадром обработки. Возвращается подтверждение с номером конфигурации; результаты маркируются этим номером. Момент применения нельзя определять только приходом нового кадра камеры, если предыдущие пиксели ещё находятся в стадиях. Нужны тайм-аут/статус ошибки при невозможности переключения; сам протокол пока не разработан.

FPGA должна иметь допустимую стартовую конфигурацию без подключения приложения. Общие принципы автономности сохраняются; пользовательская конфигурация задаёт режим, а аппаратная часть управляет его выполнением. Выходной формат и объём результата меняются только в пределах явно описанных профилей и отражаются в метаданных для ARM. Код и регистровые адреса не создавались.

Связные компоненты и сложные контуры не переносить в FPGA только ради аппаратной реализации — сначала проверить алгоритм и стоимость. ## Согласованный формат пикселя для ARM

Зафиксировано по указанию пользователя 2026-11-05. Один RAW12-пиксель хранится как беззнаковое 16-битное значение uint16_t: биты [11:0] содержат отсчёт, [15:12] равны нулю. Числовой диапазон — 0–4095. Служебные признаки строки/кадра и метаданные в старшие биты пикселя не помещаются.

Контракт порядка байтов — little-endian: для пикселя 0xABC значение слова 0x0ABC, байт по меньшему адресу равен 0xBC, следующий — 0x0A. Это согласованный формат буфера, а не результат проверки конфигурации ARM/Linux или записи DMA. Перед реализацией подтвердить порядок байтов фактической системы, разводку байтовых полос тракта DMA и при необходимости обеспечить преобразование к контракту.

Адреса буфера задаются в байтах. При последовательном размещении пиксели находятся по адресам BASE, BASE+2, BASE+4 и далее. Без межстрочного отступа шаг строки stride_bytes = width × 2, адрес пикселя (x, y) = BASE + y × stride_bytes + x × 2. При ширине 1280 шаг составляет 2560 байт, при высоте 800 полный кадр занимает 2 048 000 байт. Разрешение 1280×800 остаётся примером; если появится выравнивающий отступ, фактический stride задаётся явно в метаданных и учитывается ARM.

Ширина хранения пикселя 16 бит не определяет ширину FIFO, Avalon-ST/MM или физической шины памяти: несколько пикселей можно объединять в одну передачу. Физическая ширина и упаковка передач ещё не выбраны. Доступ к завершённому кадру, владение буферами и согласованность кэша решаются отдельно; правильный порядок байтов их не обеспечивает.

## Последовательный разбор входа и записи

Обсуждаемый пример, не утверждённые параметры камеры: параллельный RAW12 с одним отсчётом за PCLK, 12 линий данных плюс PCLK, LINE_VALID и FRAME_VALID. Такт выдаёт камера; в условном активном высоком режиме пиксели принимаются при разрешающих уровнях обоих valid. Конкретные полярности и фронт захвата берутся из документации выбранного сенсора.

Для 1280×800 хранение только плотно упакованных RAW12 даёт 1 536 000 байт/кадр; размещение каждого отсчёта в 16-битном слове даёт 2 048 000 байт. Служебные сигналы не добавляются к каждому пикселю как биты изображения. Для обсуждаемого RAW12-тракта согласовано хранение в 16-битных словах; плотная упаковка приведена только для сравнения объёма.

Перед внешней памятью рассматривается FIFO: он покрывает рассчитанные паузы обслуживания записи. При разных тактах приёма и записи используется корректный переход доменов, например асинхронный FIFO. Его глубина зависит от скорости поступления и максимального перерыва обслуживания; постоянный дефицит пропускной способности FIFO не исправляет. Для внутренней памяти с гарантированным приёмом по тому же такту отдельный FIFO не является обязательным. Конкретная память, контроллер, глубина FIFO и кадровый режим не утверждены.

Пользователь подтвердил такой уровень архитектурного разбора: физические сигналы, момент приёма, хранение и назначение следующего узла. Общая схема остаётся обзором. Ближайшее продолжение — путь FIFO → запись в память.

## Поток данных и проверка аппаратной обработки

До RTL необходимо определить контракт потока: формат и разрядность пикселя, порядок передачи, размеры изображения, признаки начала и конца кадра и строки, допустимые паузы, управление готовностью, сброс и восстановление после ошибки.

Необходимо различать темп входного потока, пропускную способность конвейера, задержку пикселя, время до завершения объекта и задержку итогового решения. Высокая частота кадров сама по себе не гарантирует короткую экспозицию или отсутствие смаза.

План проверки — одинаковый вход для программного эталона и ПЛИС. Сравниваются промежуточные данные и итоговые измерения, включая округление, насыщение, границы изображения и поведение при паузах. Ресурсы логики, памяти, достигнутая частота и качество результата фиксируются по фактическим измерениям.

Если используется DMA и общая память, отдельно определяются выделение буферов, владение ими, кэширование, готовность кадра и защита от перезаписи. Само отображение через mmap не задаёт эти правила. Zero-copy DMA из исходного ТЗ пока остаётся вариантом для оценки.

## Согласованная роль ARM HPS в анализе

Зафиксировано по поручению пользователя 2026-11-05: ARM анализирует завершённые данные FPGA и выполняет прикладной сценарий — измерения/категоризацию, подсчёт объектов, определение значения игровой кости или другую задачу. Категоризация является одним из сценариев, а не обязательным единственным выходом системы. Захват камеры, обслуживание FIFO, выдача заданий DMA и смена аппаратных буферов остаются автономными задачами FPGA. Описание ниже задаёт роль HPS, но не фиксирует окончательное распределение всех алгоритмов.

Последовательность HPS: получить дескриптор готового результата и проверить статус → получить защищённый доступ к данным → выделить/описать объекты и оценить кандидатов в дефекты в объёме, не выполненном FPGA → вычислить физические размеры при действующей калибровке → присвоить категорию или статус недостоверной оценки → сохранить решение и освободить использованный буфер. Освобождение результата не является настройкой аппаратного захвата.

Для первого программного анализа рассматриваются C++/OpenCV, поиск контуров и анализ вложенности. Конкретные библиотеки/версии и критерии дефектов ещё проверить и согласовать по реальным данным. Внутренний контур не считается самостоятельным подтверждением повреждения.

| Возможный выход FPGA | Работа ARM |
| --- | --- |
| Подготовленное изображение | Сегментация, контуры, признаки и классификация |
| Маски объектов и кандидатов в дефекты | Анализ областей, необходимые измерения и классификация |
| Характеристики объектов | Проверка признаков и классификация в пределах достаточности этих характеристик |

Выходной формат IP пока открыт. Выбирать минимальный набор данных, достаточный для проверяемого качества, сохраняя возможность получить изображение для отладки и разбора ошибок. Способность классифицировать все дефекты только по числовым характеристикам не предполагается. Размерная категория, категория качества и ботанический сорт различаются; последний оставлен на развитие.

## Геометрия и категории

Пользователь поручил предложить показатель размерной сортировки. Для нескольких ракурсов предложено объединять признаки обнаружения повреждения по одному яблоку. Суммирование площадей пятен без сопоставления ракурсов может повторно учесть одно повреждение. Полный охват поверхности ручным вращением не считается гарантированным.

## Данные и оценка качества

Планируется собирать реальные изображения годных яблок, повреждений и типовых помех. Для каждого набора нужны условия съёмки и разметка, соответствующая задаче: объект, его маска, область повреждения и при наличии подтверждения тип дефекта.

Выборки для настройки и итоговой проверки следует разделять по физическим яблокам и сериям съёмки, чтобы ракурсы одного плода не создавали утечку данных. Синтетические изображения полезны для проверки геометрии и аппаратных операций; по ним нельзя оценить распознавание реальных повреждений.

Для производительности — задержка и её распределение, пропускная способность, потери данных и объём памяти. Численные пороги и длительность испытаний не установлены.

ML и нейросети рассматриваются как последующее расширение при наличии данных и понятной задачи. Обучение не обязано выполняться на DE1-SoC. Запуск конкретной модели на плате потребует отдельной оценки.

Комплектацию Trigger/Strobe и конфигурацию перемычек необходимо заказывать или проверять явно: руководство описывает различные назначения общих контактов и опциональный разъём X2. BSP PHYTEC не является готовой поддержкой DE1-SoC.

Наличие технического PDF не означает готовность комплекта к запуску. [Страница производителя KLT](https://www.kailaptech.com/product.aspx?id=2473&l1=1413).

Коммерческий выбор остаётся открытым: нет подтверждённой цены единичной камеры с объективом, платы сопряжения, доставки и доступности поставки. Покупать по одному этому сравнению не предлагается. Следующий шаг — определить доступный канал покупки, проверить комплектность и стоимость, затем выбрать вариант либо расширить поиск.

## Возможное расширение манипулятором

Статус после уточнения пользователя: отложено на перспективу. Ни манипулятор, ни камера на руке, ни выбор из кучи не входят в текущий объём. Ниже сохранена оценка возможного развития; она не задерживает подбор камеры для неподвижного стенда.

Пользователь запросил оценку добавления руки, которая берёт яблоко и подставляет под камеру. Расширение обсуждается, в требования не включено. Сложность зависит от сценария: захват из фиксированного ложемента, поиск раздельных яблок на плоскости или захват из общей кучи. Последние варианты добавляют определение положения и захвата, калибровку координат камеры и робота, планирование движения и проверку коллизий.

Инженерные вопросы: грузоподъёмность с учётом захвата и вылета, повторяемость позиции съёмки, фиксация без повреждений, контроль успешного захвата, колебания перед экспозицией, закрытие поверхности захватом и длительность цикла. Перемещение яблока под камеру не гарантирует осмотр всей поверхности. Для промышленного развития следует сравнить манипулятор с механизмом подачи или вращения по целевой производительности. Предварительное предложение — независимый модуль манипуляции, без обязательного переноса управления приводами и планирования на DE1-SoC. Конкретная архитектура не утверждена.

Как пример состава задач планирования рассмотрена [документация MoveIt Task Constructor](https://moveit.picknik.ai/main/doc/tutorials/pick_and_place_with_moveit_task_constructor/pick_and_place_with_moveit_task_constructor.html). ROS/MoveIt не выбраны как стек проекта. Следующее уточнение: известная точка захвата или самостоятельный поиск яблока; требуется ли вращение в захвате.

### Камера на манипуляторе

Новое предложение пользователя: камера установлена на руке, робот находит яблоко, приближает камеру для осмотра и затем сортирует. Рассматривается как eye-in-hand, пока не утверждено изменение архитектуры. Механизм захвата и точная последовательность действий не определены.

Добавляются калибровка камеры относительно рабочего органа, привязка кадра к положению робота, определение расстояния/геометрии захвата, переход от обзора к близкой съёмке, контроль освещения и предотвращение перекрытия камерой или захватом. Одна монокулярная камера не даёт произвольное метрическое 3D-положение без дополнительных геометрических предположений или измерений. При известной плоскости и ограниченном разбросе объектов возможен более простой сценарий; высота яблока над плоскостью учитывается отдельно.

Согласованное ранее соединение 10–20 см нельзя автоматически распространять на движущуюся камеру. Нужны оценка прокладки и ресурса кабеля, расположения приёмника/вычислительного узла, массы и помех от приводов. При возвращении к этой перспективной схеме выбор камеры и интерфейса потребуется пересмотреть; текущий подбор ведётся для неподвижной установки. Global Shutter, RAW и аппаратный триггер сохраняются. Промышленной цели схема сама по себе не противоречит, но пригодность определяется длительностью цикла, повторяемостью и качеством осмотра, а полный обзор поверхности не гарантируется.

Источники для обсуждения: [OpenCV hand-eye calibration](https://docs.opencv.org/4.x/d9/d0c/group__calib3d.html), [Zivid о калибровке камеры на роботе](https://support.zivid.com/en/latest/camera/academy/applications/hand-eye/cautions-and-recommendations.html). Конкретный робот, приводной контроллер, транспорт и стек не выбраны.

## Согласованные корректировки концепции платформы

Все шесть рекомендаций ассистента приняты пользователем 2026-11-05 фразой «да, согласен на эту корректировку и дополнения». Ниже — согласованные направления архитектуры и требования к дальнейшей проработке. Это не подтверждение реализации или результатов испытаний. Сохраняются самостоятельные IP, возможность составного обработчика, автономность FPGA и прикладные сценарии ARM.

1. Не делать кадровый проход обязательным для всех операций. Предусмотреть два источника входного потока обработчика: подготовленный поток камеры и воспроизведение из SDRAM через DMA. Локальные последовательные операции соединять напрямую; кадровую память использовать для сохранения, повторных проходов, произвольного доступа и выдачи изображений. Разобранная схема с предварительным сохранением остаётся вариантом, но не должна автоматически стать единственным трактом. Два варианта источника приняты на уровне концепции; реализация выбора источника и его синхронизация ещё не определены.
2. Расширить контракт типов данных конструктора. Согласованный RAW12 в uint16_t описывает входной/сохраняемый RAW, но не все результаты IP. Предусмотреть явно описанные яркостные/цветовые изображения, маски, градиенты с нужной знаковостью и разрядностью, записи областей/характеристик. Тип, геометрия, метки кадра и версия конфигурации обязательны для интерпретации; нужны явные адаптеры несовместимых типов.
3. Задать проверяемый паспорт каждого самостоятельного IP: формат входа/выхода, допустимый темп, такты и правила пауз, размер локальной памяти, поведение границ, округление/насыщение и эталон проверки. Наличие одинаковых Avalon-ST портов не является полной совместимостью. Размер окна и разрядность могут быть параметрами синтеза или исполняемой конфигурации; указывать различие для конкретного IP.
4. При возвращении к отложенному переключению добавить проверку допустимости профиля до применения: типы, геометрия, требуемый темп и бюджет памяти. Не разрешать несовместимую цепочку только потому, что соединения физически существуют. Топология маршрутизации и механизм проверки остаются открытыми.
5. Сделать воспроизведение контрольного изображения штатным средством проверки. Один входной файл должен позволять сравнить результаты отдельных аппаратных IP и программного эталона, а также воспроизвести ошибку. Заранее определить наблюдаемые счётчики потерь/ошибок, идентификаторы кадров и подтверждение применённой конфигурации. VGA для этого не требуется и по указанию пользователя остаётся отложенным.
6. Явно проверить автономный запуск и деградацию. FPGA должна иметь понятный путь от включения питания до настройки камеры/памяти и обработки без исполнения управляющего приложения HPS. Разграничить сбросы, ошибки камеры, переполнения, задержку потребителя и восстановление на границе кадра. Повреждённый/неполный кадр не выдавать как корректное измерение. Конкретный автономный boot ещё не проверен на плате.

При последующей детализации первый приоритет — типизированный контракт IP и проверка бюджета памяти/темпа, затем параметры двух согласованных режимов обработки. Расширение библиотеки без этих проверок может дать набор несовместимых компонентов. Дополнительный перенос сложных алгоритмов в FPGA обосновывать измеряемой пользой и доступными ресурсами.

## Разделы последующей проработки

Добавлено по поручению пользователя 2026-11-05. Эти вопросы признаны нужными, но относятся к дальнейшей детализации перед реализацией. Они не являются поручением немедленно переходить к алгоритмам, RTL или C++. Текущее обсуждение остаётся на уровне общей концепции. По мере работы в каждом подразделе фиксировать выбранное решение, основание, способ проверки и ограничения.

### Алгоритм IP обработчика

Определить последовательность операций внутри IP: подготовка Mono/Bayer, подавление шума, выделение объектов и кандидатов в дефекты, вычисляемые признаки. Для выбранных стадий описать вход, выход, локальную память, задержку и поведение при паузах. Фильтр 3×3 ранее приводился как пример; конкретный алгоритм не выбран. Границы IP с внутренними входным/выходным FIFO и внешними DMA сохраняются.

### Состав данных для ARM

Выбрать, что публикует FPGA: подготовленное изображение, маски, участки изображения, характеристики объектов либо их сочетание. Сопоставить достаточность данных для классификации с объёмом передачи и нагрузкой ARM. Определить описание результата и возможность получить исходное изображение для проверки ошибок. Роль ARM согласована; конкретный формат выхода IP остаётся открытым.

### Рабочий цикл и временные требования

Определить непрерывную или триггерную съёмку, разрешение, частоту кадров, требуемую производительность по объектам и допустимую задержку решения. Различать частоту пикселей, кадров, завершения обработки и получения данных HPS. На этой основе обосновать глубину очередей и число кадровых буферов. Значения 1280×800, RAW12 и 60 FPS не считать автоматически утверждённым рабочим режимом камеры; согласованный формат хранения RAW12 в uint16_t сохраняется для рассматриваемого тракта.

### Владение буферами и перегрузка

Определить состояния буферов, моменты завершения записи, начала обработки, публикации, закрепления потребителем и освобождения. Исключить перезапись используемых данных. Выбрать поведение при задержке обработчика/HPS, отсутствии свободного буфера, переполнении FIFO и повреждении кадра; предусмотреть наблюдаемый статус потерь. Три кадровых слота остаются предложением до расчёта и согласования. Автономность FPGA от программного обслуживания HPS является требованием.

### Критерии правильности результата

Определить измеряемые размеры, границы категорий, перечень распознаваемых дефектов, правила неопределённого результата и допустимые ошибки. Сформировать контрольные данные и разметку, независимую проверку и сравнение аппаратного результата с программным эталоном. Кандидат в дефект и подтверждённое повреждение различаются. Конкретные численные критерии пока не утверждены.

### Пропускная способность памяти и реализуемость тракта

Проверить бюджет SDRAM для всех одновременно работающих потребителей: захват, чтение обработчиком, запись результата и доступ HPS. Учесть refresh, смену направления, burst и арбитраж. Для разобранного примера 1280×800, 16 бит, 60 FPS один полный проход записи/чтения/записи составляет 368,64 МБ/с полезного трафика без доступа HPS; это расчёт нагрузки, не достигнутая скорость платы. По проверке выбрать кадровый или потоковый вариант стадий либо явно скорректировать режим/аппаратуру. Производительность не выводится только из объёма SDRAM.

### Состав библиотеки самостоятельных IP ядер

Определить перечень независимых IP: подготовка пикселей, различные фильтры, градиенты, пороги, морфология и другие операции. Для каждого описать тип входа/выхода, параметры, локальную память, задержку и проверки. Рассмотреть отдельные специализированные IP и параметризуемые IP, например свёртку с выбираемыми коэффициентами. Концепция самостоятельных IP-ядер подтверждена; конкретная библиотека ещё не выбрана.

### Коммутация IP ядер и управление из приложения

Вопрос отложен пользователем для дальнейшего обсуждения. Сохранить возможность выбора комбинаций имеющихся IP-ядер из приложения через ARM. Позднее сравнить переключаемые стадии с bypass и другие варианты соединений, допустимые порядки ядер, совместимость форматов, расход ресурсов и пропускную способность. Определить параметры профиля, механизм безопасного применения, подтверждение и привязку конфигурации к результату. Ни конкретная топология, ни регистровый протокол не утверждены. Уровень объяснения учитывать опыт пользователя в embedded/FPGA; различие переключения существующих ядер и добавления новых ему понятно.

## Основной тракт изменён на прямую потоковую обработку — 2026-11-05

Пользователь предложил перейти к прямой потоковой обработке с внутренней памятью FPGA, чтобы уменьшить задержку и потенциально стоимость будущей собственной платы. Принято как направление первого этапа; это развитие ранее согласованного режима прямого потока, а не отказ от универсальности платформы. Поиск старого SDRAM IP, обязательные кадровые DMA и внешняя SDRAM исключены из критического пути первого этапа. На имеющейся DE1-SoC SDRAM физически остаётся, экономия компонентов возможна при разработке своей платы и подтверждённой достаточности выбранной архитектуры.

Базовая схема: камера -> RAW-приём/форматирование -> входной FIFO (CDC при разных тактах) -> цепочка самостоятельных потоковых IP с локальными строковыми/оконными буферами -> FIFO/буфер завершённых результатов -> согласованный интерфейс HPS. Конкретный набор ядер ещё не выбран. Выход может содержать нейтральные характеристики/маски/пиксели по профилю; объём и возможность передачи каждого типа без кадровой памяти требуют расчёта. DMA не объявляется ненужным вообще: он может потребоваться для передачи в HPS или дополнительного кадрового режима. FPGA не получает предметные понятия яблока/дефекта; ARM по-прежнему интерпретирует результаты.

Основные условия: считать память всех ядер и FIFO вместе, а не одного фильтра; локальная RAM расходуется блоками с ограниченными конфигурациями ширины/глубины. Для 3x3 при 1280 пикселях и хранении 16 бит на пиксель две строки содержат 5120 байт полезных данных плюс регистры окна/служебное хранение; это пример, не итоговый ресурсный отчёт. Каскад фильтров может потребовать отдельные строковые буферы для каждой стадии. Потоковый подсчёт/статистика возможны, но связные области требуют ограниченных таблиц меток/объединений и политики переполнения. Полный кадр для программной классификации, ретроспективный ROI или повторный проход без новой съёмки потребуют отдельного хранения/изменения алгоритма; обещание всех исходных функций без кадровой памяти не дано.

Темп камеры обычно нельзя остановить сигналом ready. Требуется подтвердить пропускную способность каждого ядра, ограниченные паузы, размеры FIFO и поведение при переполнении/задержке HPS. Потоковый конвейер уменьшает задержку и исключает обязательный трафик кадрового чтения/записи, но не повышает автоматически FPS камеры; итоговые характеристики кадра доступны после поступления необходимых данных.
